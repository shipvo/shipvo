## How times are taken

- **Pointer published**: the time the pointer file became visible on the server.
- **Healthy**: the time the server received the app's `applied` telemetry for the new release, sent after `markHealthy`.
- **Download and apply**: the runtime's own `downloadMs` (fetch, patch, verify) and `apply_ms` (in-process reload) from telemetry. Sizes come from the server log.
- **Cold start**: `adb shell am start -W` TotalTime, and the runtime's `coldStartMs` (process start to `markHealthy`).
- On-device state (current, pending and blocked release, cohort, bundle file hash) is read with `run-as` from the runtime's preferences and files.

The app polls every 10 s while open. Pointer-to-healthy therefore depends on where in the poll cycle the publish lands. Individual trials are shown below.

### What each safety scenario checked

- **Tampered bundles.** For each of bad signature, bad hash and bad size, a release was published, the device was left running for 35 s (three or more polls), then:
  - the app was still alive;
  - `current_release` was unchanged (7) and `pending_release` was 0;
  - no telemetry for the tampered release;
  - after a force-stop and relaunch the app came up on release 7.

  A bad signature was rejected before any bundle download. A bad hash and a bad size were rejected after the download. A valid release then applied normally.
- **Rollback.** The earlier bundle was republished as a new release, as `shipvo rollback` does. The device applied it and the SHA-256 of `files/shipvo/r<N>.hbc` on the device matched the target bundle in all 3 trials. This covers fleet rollback. The on-device `Runtime.rollback()` call is not driven by this harness.
- **Crash-loop.** A bundle that throws at startup was published. The device staged it, and crashed on the reload. The runner then relaunched the app until it was healthy. In all 3 trials it took 3 launches: the bad release booted on the reload and on the first 2 launches, and the 3rd launch came up on the previous release. After that `blocked_release` equalled the crash release, `current_release` was the previous good release, the app reported `crash_loop_revert`, and the server saw no further download of the bad bundle.
- **Staged rollout.** A release was published only to bands `b0` and `b1`. The device is in `b2`. Over 35 s it polled its own band 4 times, never fetched the new release's bundle or patch, never reported it, and kept release 14. Publishing the same release to `b2` then applied it in 6,259 ms.

## Findings worth knowing

- **The embedded bundle and the OTA bundle differ.** The APK's embedded bundle is 1,522,512 B and the OTA bundle of the same source is about 1,876,565 B. This is the first-patch gap already listed in `docs/spike-results.md` (gap 1). A first update after install sends 333 KB rather than a few KB for that reason.
- **Rejected updates are not reported.** The runtime records `verify_failed:<release>` in its event list when a hash or size check fails, but the sample app only reports `crash_loop_revert` and `rolled_back` to telemetry. A tampered or corrupted release is therefore visible on the server only as repeated downloads. This is not a failing scenario, so no issue was filed.
- **A device in a band outside the rollout still gets HTTP 200** for its band's previous pointer. It ignores it because the release is not newer. The harness checks for downloads of the new release, not for a 404.
