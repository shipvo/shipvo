# Device Lab report, 2026-11-07

Raw data: [`2026-11-07.json`](2026-11-07.json). Previous report: [`2026-11-06.md`](2026-11-06.md). Harness: [`scripts/android-e2e/`](../../../scripts/android-e2e/README.md).

**15 of 15 scenarios passed** in the final run. No safety scenario failed. No timing is more than 20% worse than the previous report, apart from two small-sample items explained below (patch download time +19%, patch size with changed content +46%). I filed no issue.

The first two runs on this APK did not pass everything. Both failures were in the harness, not on the device:

- Run 1 (12 of 15): "bad hash" and "bad size" failed. The device did the right thing (bundle downloaded, rejected, release 9 kept running, relaunch on release 9). The harness treated any telemetry for the rejected release as "the release ran". Since #752 the runtime also reports the refusal under that release. The check now looks for an `applied` event only. The rollback scenario failed too (see run 2).
- Run 2 (14 of 15): `Runtime.rollback()` failed with "button not found". The sample app now opens on the shop home screen and the button is on "About this build", which sits below the fold (`uiautomator` reports it with bounds `[0,0][0,0]`). The scenario now swipes up until "About this build" has bounds, opens it, then finds the button. `tapTarget` ignores nodes with empty bounds (new unit test).
- Run 3 is the table below. Runs 1 and 2 had timings in the same range (their reports are not kept).

### Safety scenarios

- **Tampered bundles**: bad signature rejected before download. Bad hash and bad size rejected after download (the app fetched the bundle again on later polls and rejected it each time). The app stayed alive on release 9 each time, restarted on release 9, and a valid release then applied.
- **Hermes bytecode mismatch**: release 13 declared for bytecode 98 on a shell with 99. The device polled the pointer, never fetched the bundle, blocked release 13, stayed on release 9. The refusal reason was in telemetry.
- **Rollback**: the earlier bundle was republished as a new release. The SHA-256 of the on-device bundle matched in 3 of 3 trials. The on-device call (`Runtime.rollback()` from the sample app's button) restored the previous release, which stayed after a force-stop and relaunch. The rolled-back release was blocked and not downloaded again.
- **Staged rollout**: published to `b0` and `b1` only. The device (band `b2`, cohort 573 in this run) polled 4 times, downloaded nothing of the new release and stayed on the running one. Widening applied it in 6,102 ms.
- **Crash on start**: in 3 of 3 trials the bad release got 3 boots, was discarded, and the previous release came back.
- **Late crash**: in 3 of 3 trials the bad release ran 3 times and the previous release came back. Trials 1 and 3 were promoted without a trial stage (`staged: false`), trial 2 went through the trial-boot path. All three restored in 52 to 62 s.
- **Resumed download**: the server cut the first response at 1,010,331 B. The app retried on the next poll with `Range: bytes=1010331-`, got a 206, and the release became healthy.

Two rows are more than 20% off and I did not file an issue for either:

- Patch download time +19% is 7 ms on three to four tiny samples (28 to 53 ms across trials), inside the spread of one run.
- Patch size with changed content is +46% against 2026-11-06 but +3% against 2026-11-05 (27,209 B). The 2026-11-06 value (19,235 B) is the outlier. Patch size here depends on how the Hermes bytecode of two bundles differs, and the harness changes only a headline. I read this as noise from the bundle build, not a runtime change. If the next report stays near 28,000 B this is settled.

The late-crash restore time went from 128 s to 53 s with 3 launches in every trial. Issue #617 (late-crash revert slow on the non-trial path) is closed, and this run does not reproduce the slow path (trials 1 and 3 took the non-trial path and restored in 53 s and 62 s). Three trials show this run only.
