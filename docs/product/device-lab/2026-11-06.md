# Device Lab report, 2026-11-06

Raw data: [`2026-11-06.json`](2026-11-06.json). Previous report: [`2026-11-05.md`](2026-11-05.md). Harness: [`scripts/android-e2e/`](../../../scripts/android-e2e/README.md).

**13 of 13 scenarios passed** in the final run. No safety scenario failed. One number is more than 20% worse than the previous report (late-crash restore time, median 128 s against 54 s). Both paths stay within 3 runs of the bad release. I filed #617.

A first run on the same APK passed 12 of 13. The failing scenario was the Hermes bytecode mismatch one. The device did the right thing (release blocked, bundle never downloaded, release 9 kept running). The harness looked for the refusal reason in telemetry before it relaunched the app, but the sample app sends the runtime's queued events only when it starts (`consumeEvents` in `App.tsx`). The reason did arrive after the relaunch (server log, release 13, `hermes_bytecode_mismatch`). I changed `scripts/android-e2e/run.mjs` to relaunch first and then wait for the reason, and re-ran everything. The table below is the second run. All other numbers in the first run were in the same range.

### Safety scenarios

- **Tampered bundles**: bad signature rejected before download; bad hash and bad size rejected after download. The app stayed alive on the current release each time, and a valid release then applied.
- **Hermes bytecode mismatch**: release 13 was declared for bytecode 98 on a shell with 99. The device polled the pointer, never fetched the bundle, blocked release 13, stayed on release 9 and came back on release 9 after a relaunch. The telemetry reason arrives only after the next app start (see the first-run note above).
- **Rollback**: the earlier bundle was republished as a new release. The SHA-256 of the on-device bundle matched in 3 of 3 trials. The on-device `Runtime.rollback()` call is not driven.
- **Staged rollout**: published to `b0` and `b1` only. The device (band `b2`, cohort 781) polled 4 times, downloaded nothing of the new release and stayed on release 17. Widening applied it in 6,257 ms.
- **Crash on start**: in 3 of 3 trials the bad release got 3 boots, was discarded, and the previous release came back.
- **Late crash**: the bad release ran at most 3 times in all trials and the previous release came back. Trials 1 and 2 were promoted without a pending trial stage (`staged: false`): 4 launches, first crash at about 75 s, restored at about 128 s. Trial 3 went through the trial-boot path: 3 launches, restored at 51.9 s. The median of 128 s is the slow path. Filed as #617.

## Act on it

- Filed: late-crash revert takes 128 s on the non-trial path, #617. Not `priority:high`: the 3-run limit held.
- No scenario failed in the final run, so no safety issue.
- Harness fix: the Hermes mismatch scenario now waits for the telemetry reason after the relaunch. Without it the scenario fails on a correct device.
- Open `device-lab` issues #589 (simulator text grouping) and #110 (Phone Harness spike, already done in the 2026-11-05 report) need no emulator work, so I took neither.
