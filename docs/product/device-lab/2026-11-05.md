### Safety scenarios: what they showed

- **Tampered bundles**: bad signature rejected before any download; bad hash and bad size rejected after download. In all three the app stayed alive, `current_release` stayed 7, `pending_release` was 0, and a relaunch came up on release 7. A valid release then applied.
- **Rollback**: the earlier bundle was republished as a new release. The SHA-256 of the on-device bundle matched the target in all 3 trials. The on-device `Runtime.rollback()` call is still not driven.
- **Staged rollout**: published to `b0` and `b1` only. The device (in `b2`) polled its own band 4 times, fetched nothing of the new release, and stayed on release 14. Widening to `b2` applied it in 6,416 ms.
- **Crash on start**: see the trial table above. In every trial the previous release came back, the bad one was blocked, `crash_loop_revert` was reported, and the bad bundle was not downloaded again. The failure is that trial 1 needed 6 launches (limit used by the harness: the bad release runs at most 3 times). Cause not found. I did not reproduce it by hand. Runs 1a and 1b did not show it.
- **Late crash (5 s after `markHealthy`)**: the runtime does not revert. Cause, measured on the emulator by polling `shipvo.runtime.xml` once a second while the app booted release 20:

  | Time into boot | `unhealthy_boots` |
  | --- | --- |
  | 2 to 6 s | 1 |
  | 7 s onward | 0 (and stays 0) |

  The JS error fired at 29.797 s on the logcat clock, process start 23.957 s. Logcat shows `ReactHost.handleHostException`, then `ReactContext.onHostPause()` and `onHostDestroy()` within 10 ms. The process was not killed (no `FATAL EXCEPTION`; the harness had to `force-stop` it), so the app is left blank. The count went to 0 about 1 s later, 24 s before the 30 s stability window. The code path is `ShipvoRuntimeModule`'s `OnActivityEntersBackground { stableNow() }`, which clears the count through `BootRules.markStableIfHealthy`. I did not add logging in `stableNow()` to confirm that exact call, so the link is the timing match plus the code. It is the same finding as #102, which is closed, while the behaviour is still present on this commit.

Behaviour changes since 2026-11-04: the crash-loop scenarios now include the late-crash case (added with #62), and it fails. The crash-on-start scenario passed in 3 of 3 trials on 2026-11-04 and passed in run 1, but failed on one trial in run 2.
