### The crash-on-start failure was a harness bug

In runs 1 and 2, trial 1 of "crash on start" needed 6 launches. The runtime was right. The harness was wrong:

- The staged-rollout scenario runs just before it. Widening that rollout put the device on release 15. The harness did not record release 15 as the running release, so it expected release 14 to come back after the revert.
- In trial 1 the runtime did the correct thing: three trial boots of the crashing release, then it discarded and blocked it and came back on release 15 (telemetry in run 1: a `crash_loop_revert` report, then three cold-start `applied` reports for release 15 before the one for release 14).
- The harness was waiting for release 14 to report healthy. It never did, so the harness force-stopped the good release 15 as a "hung boot" three times. That pushed release 15's own boot counter to 3 and the runtime reverted release 15 to release 14. Only then did the harness see what it was waiting for.
- Trials 2 and 3 passed because trial 1 had left the device on release 14, which is what the harness expected.

The fix is one line in `scripts/android-e2e/run.mjs`: after the staged-rollout scenario, record the widened release as the running one. With it, all three crash-on-start trials passed with 3 launches. This also explains the "6 launches in 1 of 6 trials" in #119 and the one failed trial in the earlier 2026-11-05 report: both were trial 1 after the staged-rollout scenario.

I also added a line to the harness that saves `adb logcat` to the work directory when a crash-loop trial takes more than 3 bad launches. Run 2 produced such a log; it showed the crash bundle's `device-lab: crash on start` error on the first two boots.

The late-crash scenario (a release that throws 5 s after `markHealthy`) passed in all three runs: it is reverted. The earlier 2026-11-05 report (before the fixes in #105) showed it never reverting. This confirms the fix for #102 and #118 on this commit.

### Safety scenarios: what they showed

- **Tampered bundles**: bad signature rejected before any download; bad hash and bad size rejected after download. In all three the app stayed alive, `current_release` stayed 7, `pending_release` was 0, and a relaunch came up on release 7. A valid release then applied.
- **Rollback**: the earlier bundle was republished as a new release. The SHA-256 of the on-device bundle matched the target in all 3 trials. The on-device `Runtime.rollback()` call is still not driven.
- **Staged rollout**: published to `b0` and `b1` only. The device (in `b2`) polled its own band 4 times, fetched nothing of the new release, and stayed on release 14. Widening to `b2` applied it in 6,098 ms.
- **Crash on start**: in each trial the bad release got 3 boots, was discarded and blocked, `crash_loop_revert` was reported, the previous release came back and the bad bundle was not downloaded again.
- **Late crash**: the bad release is counted as it runs after being promoted. Trials 1 and 2 used 3 runs of the bad release plus the revert launch (4 launches); trial 3 used 2 plus the revert (3 launches). All are within the limit of 3 runs.

- Its parts are lower: download 38 ms (47 ms) and apply 94 ms (140 ms). Download plus apply is 132 ms now and 187 ms then.
- Pointer to healthy also contains where the publish landed in the app's 10 s poll cycle. Three patch trials in run 1 gave 232, 308 and 343 ms; in run 3, 362 and 374 ms (plus one 10.7 s poll miss). The median of runs 1 and 3 together, leaving out the poll miss, is 343 ms (+17%); the 2026-11-04 trials were 284 to 334 ms.
- The same measure for the full bundle and for rollback went down.

If the next report shows the patch pointer-to-healthy above 353 ms (20% over 294 ms) again with download and apply not higher, that is worth a look at the poll and the telemetry send.

Issue #103 reported cold start and apply 23% to 45% above 2026-11-04 on an Intel Xeon 8370C host. On this host (a third CPU type, EPYC 9V45) they are 19% to 37% below. Together with the EPYC 9V74 result in the earlier 2026-11-05 report, this supports "host variance". It is still not a measurement on the Xeon, so #103 stays open.
