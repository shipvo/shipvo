### The failing scenario: crash after markHealthy

A bundle that throws 5 s after start was published. The device staged it, reloaded into it, and the release reported healthy.

- The JS error is handled by React Native as a host exception: logcat shows `handleHostException`, then `onHostPause()` and `onHostDestroy()`. **The process does not die.** There is no `FATAL EXCEPTION` and the process id does not change. The user sees a dead app.
- In a single-release repro polled every 0.5 s, the promoting boot set `unhealthy_boots=1` at 04:18:05.8, the error hit at 04:18:09.19, and `unhealthy_boots` was `0` by 04:18:10.8. The 30 s stability window would have ended at about 04:18:35.8. The counter is cleared 1.6 s after the crash.
- The likely cause is that `OnActivityEntersBackground` (fired by the host pause) calls `markStableIfHealthy`. This is not confirmed in code. It is in the issue.
- In the full run the harness relaunched the app up to 10 times per trial. `current_release` stayed on the bad release, no `crash_loop_revert` was reported, and `blocked_release` did not change.

Crash-on-start (the other crash-loop scenario) passes: 3 launches, previous release restored, the bad bundle was not downloaded again.

### What each safety scenario checked

- **Tampered bundles.** For each of bad signature, bad hash and bad size, a release was published and the device left running for 35 s. The app stayed alive, `current_release` stayed 7, `pending_release` stayed 0, there was no telemetry for the tampered release, and a relaunch came up on release 7. A bad signature was rejected before any bundle download. A bad hash and a bad size were rejected after the download. A valid release then applied normally.
- **Rollback.** The earlier bundle was republished as a new release, as `shipvo rollback` does. The SHA-256 of the bundle file on the device matched the target in all 3 trials. The on-device `Runtime.rollback()` call is not driven by this harness.
- **Staged rollout.** A release was published only to the two bands that do not include this device. Over 35 s the device polled its own band 4 times, never fetched the new release, and kept its release. Widening the rollout to its band applied it in 6,476 ms.

## Harness change in this PR

The staged-rollout scenario ran straight after the late-crash scenario. The failed late-crash scenario left the app on the crashing release with a dead React host, so the device did not poll at all and staged rollout failed in the first full run (0 polls). The runner now publishes a known good release, relaunches, and waits for it to be healthy before the staged-rollout scenario. In the second run staged rollout passed. This does not hide the late-crash failure, which is still reported.

If the restore fails, the runner records a failed scenario "restore a good release before the staged rollout scenario" and skips staged rollout. In both runs the restore succeeded, so it wrote no scenario entry; that is why the JSON has 12 scenarios and none for the restore. The failure path is covered by a unit test of `restoreGood` (stubbed publish, relaunch and wait), not by a device run.

## Not covered yet

- Shell upgrade (installing a newer APK over an old one discards OTA bundles). Needs a second APK build.
- The on-device `Runtime.rollback()` call.
- Low-memory and slow-network conditions (the emulator network is not throttled).
- Hosts of the same CPU type across days, to separate host variance from regressions (#103).
