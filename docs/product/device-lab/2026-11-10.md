### First update after install (issue #1397)

Issue #1397 reported 556 ms from pointer fetch to patch request on the first update after install, against 59 ms in the report before, from one trial each. The scenario now uninstalls, installs and starts the shell for each of 3 trials, waits for the bundled release to report healthy, then publishes.

| Trial | Pointer fetch to patch request | Patch received to staged | Staged to healthy |
| --- | --- | --- | --- |
| 1 | 78 ms | 349 ms | 189 ms |
| 2 | 37 ms | 438 ms | 183 ms |
| 3 | 37 ms | 221 ms | 288 ms |
| Median | **37 ms** | 349 ms | 189 ms |

The gap is 37 to 78 ms on 3 fresh installs. In these trials the app fetched the pointer within 2 ms of publish, because it was already polling after its first start.

The slow case repeats elsewhere in this data. When the poll timer fetches the pointer seconds after publish, the patch request follows about 500 ms later:

| Run | Pointer seen after publish | Pointer fetch to patch request |
| --- | --- | --- |
| Issue #1397 | 8,359 ms | 556 ms |
| Earlier run of this day, patch trial 4 | 9,741 ms | 504 ms |
| This run, full-bundle trial 2 | 10,349 ms | 505 ms |

When the pointer is fetched within a few ms of publish, the gap is 5 to 78 ms. The 3 fresh-install trials all fall in the second group, so their 37 ms median does not measure the timer case.

A first attempt of this change failed in trial 3: the fresh install fetched the pointer left over from trial 2 and applied release 2 before the harness published release 3, so release 3 had no embedded-bundle base and went out as a full bundle. The harness now deletes the old pointers before each reinstall. The second run, reported here, passed all three trials with patches.

### Safety scenarios

- **Tampered bundles**: bad signature rejected before download. Bad hash and bad size rejected after download. The app stayed alive on release 11 each time, restarted on release 11, and a valid release then applied.
- **Hermes bytecode mismatch**: release 15 declared for bytecode 98 on a shell with 99. The device polled the pointer, never fetched the bundle, blocked release 15, stayed on release 11. The refusal reason was in telemetry.
- **Rollback**: the earlier bundle was republished as a new release. The on-device call restored release 20, which stayed after a force-stop and relaunch. Release 21 was blocked and not downloaded again.
- **Staged rollout**: published to `b0` and `b1` only. The device (band `b2`, cohort 827) polled 4 times, downloaded nothing of the new release and stayed on release 20. Widening applied it in 6,000 ms.
- **Crash on start**: in 3 of 3 trials the bad release got 3 boots, was discarded, and the previous release came back.
- **Late crash**: in 3 of 3 trials the bad release ran 3 times and the previous release came back, in 60.7 to 61.4 s.
- **Resumed download**: the server cut the first response at 1,010,392 B. The app retried on the next poll with `Range: bytes=1010392-`, got a 206, and the release became healthy.
