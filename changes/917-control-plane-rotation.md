- `control-plane`: new `POST /rotation/<app>` and `PUT /rotation/<app>/root` (admin session only; publish tokens, the owner token and `sv_test_` login keys get 403) store root-signed key rotation statements. Pointer responses gain a `rotations` array (at most 8, ascending). Each upload writes a `key-rotation` audit row.
- Migration: `0022_key_rotation.sql` adds `rotation_roots`, `rotations` and `audit_log_v2` (the audit table with `key-rotation` allowed; existing rows are copied). `GET /audit/<app>` now reads `audit_log_v2`. Additive; running it twice raises no error, but run it once, then deploy the Worker. Do not run it again: the copy keeps old ids, and a second run would skip old rows whose id is already used in `audit_log_v2`. Audit rows written to `audit_log` between the migration and the Worker deploy stay in `audit_log` and do not appear in `GET /audit`.
